# Тестовые задания

Раздел с решениями тестовых заданий по вакансии. Лежит рядом с основным
проектом [Тендер-радар](../README.md), но живёт по своим правилам: это
законченные ответы на внешние требования, а не фазы продуктового плана.

**Фазовый цикл `SPEC_PLAN/` сюда не распространяется.** `PROGRESS.md`,
`HANDOFF.md`, `IMPLEMENTATION_PLAN.md` и `phase-registry.md` отражают
состояние продукта и решениями из этой папки не затрагиваются. Из процесса
взята только дисциплина исполнения: атомарные коммиты, разбор решения в
markdown, ничего не считается сделанным без зелёной проверки.

## Решения

| № | Задание | Стек | Что внутри |
|---|---|---|---|
| 4 | [Проектирование схемы БД «Тендерная площадка»](task-04-db-schema/SOLUTION.md) | PostgreSQL 16 | 5 таблиц, 9 FK, 36 индексов, генератор данных на ~450 тыс. строк, 3 аналитических запроса, планы выполнения до/после оптимизации |
| 6 | [Микросервис трекинга статусов тендеров](task-06-tender-status-api/SOLUTION.md) | Python 3.12, FastAPI, SQLAlchemy 2.0 (async) | 6 эндпоинтов, машина состояний, аудит переходов, 34 теста против настоящего PostgreSQL, Docker |

Задания связаны: сервис из №6 работает поверх схемы из №4 и не заводит
своих копий таблиц. Статусы тендера (`draft` / `active` / `won` / `lost`)
заложены в схему один раз и используются обоими решениями — два разных
набора статусов на одну сущность неизбежно разошлись бы.

## Связь с основным проектом

Схема задания 4 — развитие модели данных Тендер-радара
([`supabase/migrations/0001_init.sql`](../supabase/migrations/0001_init.sql)),
где закупка представлена плоской записью извещения из ЕИС. В задании она
разворачивается в полноценную площадку: лоты, ставки участников, исполнение
контрактов.

Основной проект при этом не менялся: `web/`, `n8n/` и `supabase/` остались
как были.

## Проверено на контейнерах

Оба стенда подняты и прогнаны целиком: схема и данные накатываются
init-скриптами, аналитика отрабатывает, планы воспроизводят замеры из
разбора (16.9 мс → 4.4 мс), сервис задания 6 стартует после healthcheck
БД и корректно отрабатывает жизненный цикл тендера, отказы по
недопустимым переходам и запись аудита. Стенды используют разные порты
(5433 и 5434) и могут работать одновременно.

## Быстрая проверка

```bash
# Задание 4 — схема, данные, аналитика
cd task-04-db-schema && docker compose up -d
docker compose exec -T db psql -U tender -d tender_platform -v ON_ERROR_STOP=1 < 01_schema.sql
docker compose exec -T db psql -U tender -d tender_platform -v ON_ERROR_STOP=1 < 02_seed.sql
docker compose exec -T db psql -U tender -d tender_platform < 03_analytics.sql

# Задание 6 — сервис
cd ../task-06-tender-status-api && docker compose up --build   # http://localhost:8000/docs
```
