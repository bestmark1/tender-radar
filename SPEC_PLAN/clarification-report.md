## 3. Риски от незакрытых/допущенных вопросов

- **Q8 (две БД)** — наибольший архитектурный риск этой стадии. Нужно явно развести: Supabase Postgres = бизнес-данные; внутренняя Postgres N8N = служебная. Архитектор обязан описать связь и то, что N8N пишет результаты именно в Supabase, а не в свою БД.
- **Q11 (MAX)** — внешняя зависимость с неизвестной зрелостью. Не блокирует MVP, т.к. есть fallback-каналы.
- **Задача 0 (токен ЕИС)** — единственный жёсткий внешний блокер. Без токена US-2 не стартует. Действие на стороне пользователя.

## 4. Что можно безопасно делать уже сейчас (не дожидаясь уточнений)

- Поднять скелет репозитория: `docker-compose` (n8n + Postgres + Redis), Next.js-приложение, подключение Supabase.
- Спроектировать схему БД (radars, tenders, matches, notifications, deadlines).
- Сделать CRUD радаров во фронте + Supabase (US-1) — не зависит от ЕИС.
- Заготовить N8N-воркфлоу со структурой нод и заглушкой вместо реального SOAP-вызова, чтобы потом подставить токен.
- Настроить Error Workflow, защиту вебхуков, экспорт воркфлоу в git.

## 5. Действие на стороне пользователя (Задача 0 — блокирующая US-2)

1. Зайти на Госуслуги → раздел регистрации потребителя машиночитаемых данных ЕИС.
2. Выбрать «Физическое лицо, индивидуальный предприниматель».
3. Получить токен (`individualPerson_token`).
4. Передать токен в `.env` N8N (НЕ в git).

> До получения токена разработка идёт по п.4 (всё, кроме реального SOAP-вызова к ЕИС).
